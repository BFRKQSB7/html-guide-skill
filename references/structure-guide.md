# 文档类型 → 结构映射

Step 2 的判定依据。**先判定类型，再按本文件对应章节组织页面骨架。** 判定不是死的：
多数内容是混合的，识别主体类型 + 叠加次要类型的局部组件。

---

## 判定 signals（看内容里有什么）

| 内容信号 | 主体类型 |
|---|---|
| 命令序列、步骤编号、流程、操作顺序、before/after | `procedure` |
| 概念、机制、原理、为什么、工作原理 | `explainer` |
| 方案对比、选型、优缺点、权衡、该选哪个 | `decision` |
| 术语表、配置项、命令速查、API 清单 | `reference` |
| 大量代码、配置文件、目录结构 | `code-guide`（叠加态） |

遇到信号冲突时，问自己：**读者读完这份页面，最想带走什么？** —— 带走「步骤」就是
procedure，带走「理解」就是 explainer，带走「该选哪个」就是 decision。

---

## 跨类型通用原则（网络研究交叉验证）

这些原则适用所有类型，写正文前先过一遍：

- **动笔前三问（分析先行）**：动笔前先显式写下——①一句话结论 ②2~6 个子主题
  ③子主题间的结构关系（流程 / 层级 / 对比 / 因果）。分析先行决定页面骨架质量；
  跳过分析直接套模板，是"AI 味"和结构失衡的来源（visual-explainer 的同类实践：
  生成前必须写 Core Concept / Sub-topics / Relationships）
- **开头给结论/产出**：explainer 第一句给答案；procedure 第一段写「做完能得到什么」。
  禁「在本指南中，你将学到…」套话（Diátaxis 点名反对）——直接给终点，读者才有方向。
- **每步闭环**：动作类内容的每一步都给「预期结果」（`.step-result`），读者做错能立刻
  察觉，信心不被"静默失败"打垮（Diátaxis + Stripe 实践）。
- **动作与讲解分离**：教程里只写"先做 x，再做 y"；解释原理的文字一律外链或放进
  `<details class="fold">` 折叠，别在步骤里长篇讲道理（Diátaxis）。
- **前置要求显式化**：缺前置是教程失败头号原因。开头用 checklist 或「开始之前」
  callout 交代环境与前提（MDN 固定以 "What you should already know" 开场）。
- **页末收尾**：结尾给「关键点回顾 + 自测/清单 + 下一步/相关」，把读者引导到下一站
  （Stripe 以测试卡表 + "See also" 收尾，MDN 以 "What's next" 收尾）。
- **元信息**：hero 给难度徽标、类别 badge、技术 chips；阅读时长由骨架自动估算。
- **长页面提示 Ctrl+K**：explainer/reference 等长页，开头用一句 callout 提示
  「按 Ctrl+K 快速跳转章节」。
- **表格一眼看全**：表格默认不横向滚动——列多先精简/合并/拆表；竖向过长（>12 行）
  用 `details.fold` 折叠（见 design-system §4.4）。综合对比表是选型页的核心，务必能整表阅读。
- **有真实得分就给图**：对比/横评若收集到基准得分（AA 指数、Elo、Benchmark 分等），
  用 `.barchart` 横向柱状图 + 得分明细表呈现，别只堆文字（design-system §4.29）。
  缺项标 `—`，厂商自报标注「待独立核实」。
- **占比/构成数据用环形图**：厂商份额、难度分布等「部分占整体」数据，用 `.donut` 环形图 +
  图例呈现（design-system §4.30）——柱状图管高低排序，环形图管占比构成，按数据关系选。
  占比相加要对得上 100%（或标注「其他」）。
- **图/表/文三条路，按数据关系选**（Abela Chart Chooser / FT Visual Vocabulary 交叉核实）：
  - **非量化结构**（流程 / 层级 / 时序 / 循环）→ 用**图示**：流程图、时间线、树状、环形循环
    （design-system §4.32–4.33）。有「是/否判断」→ 流程图；事件按时间展开 → 时间线；
    层级包含 → 树状；循环往复 → cycle。
  - **量化数据**（高低排序 / 占比构成）→ 柱状图（§4.29）或环形图（§4.30）。
  - **精确数值需比读**（价目、参数、规格）→ **表格**。
  - **三行内能说清** → 直接文字，别为图而图。
  - 判断主轴：读者要「**看出关系**」用图、「**查精确值**」用表、「**听解释**」用文字。
    一条规则：图必须比文字多给一层信息（模式/趋势/位置），否则就是装饰。
- **防废话（Strunk&White / Google 技术写作 / NN/g 原文核实）**，写完正文逐条自查：
  1. **删句测试**——删掉任一句后段落语义不变 → 删。每条必须带来新信息（Strunk「make every word tell」）
  2. 删三类套话：以「值得注意的是 / 请注意」开头的、「在本指南中你将学到…」式预告句
    （Diátaxis 点名抨击）、「总之 / 综上所述」式无新信息收尾
  3. **一句一想法**：超 25 词或含并列列表的长句拆开（Google 技术写作）
  4. 每段一个主题、3–5 句，离题句删除或外移
  5. 主动语态 + 强动词；消灭「there is/are、you can、is able to、in order to」
  6. 能列则列：清单 / 表格替代散文，每项一句，前置引导句
  7. **结论先行**：每节首句给结论，页首 TL;DR；深度内容外链或进折叠，别内联
    （Diátaxis：完整性靠链接，不靠把每件事都塞进正文）
- **生动化 = 扫读锚点，不是装饰**（NN/g：79% 用户只扫读；防 AI slop）：
  - 加组件前问「读者跳过它会损失信息或定位吗？」损失→留，只好看→删
  - 长节（>3 屏）末尾用 `.takeaway` 收束 1–3 条；长文页首用 `.tldr`（≤3 条，别复述标题）
  - 有**可溯源**的关键数字用 `.stat` 大数字（标注口径/出处）；有普遍误解用 `.mythfact` 红绿对照
  - 金句用 `.pullquote`（一屏 ≤1）、正文首段 `.dropcap`（全文 ≤1）
  - **一屏 ≤2 个「大声」元素**（大标题/大数字/拉引），其余安静；避免「圆角卡片+厚色条」
    这类 AI 签名（design-system §1.5 / §2.1 / §4.35）
- **术语首现注记**：生僻专业词首次出现用 `.term` 给一句话定义（如 `quota<span class="term">订阅额度池</span>`），
  读者才看得懂；显然词（URL/API）不注、正文已解释的不重复、只首现注（design-system §4.36）。
- **风格（软默认）**：正文写完后在 `<html data-style="...">` 定观感——新闻综述/大事记→`newspaper`、
  观点长文/深度讲解→`magazine`、数据横评/速查→`minimal`、论文/规范→`academic`、默认→`modern`。
  数据页别硬套报纸风；先写正文最后定风格（design-system §2.2）。

## A. procedure 操作教程

**适用**：安装指南、操作流程、复现步骤、DIY、从零搭建。

推荐章节骨架（按此顺序，缺失环节可跳过）：

```
hero（标题/对象/前置）
1. 目标与产出          —— 做完能得到什么；需要哪些前置条件/工具（清单）
2. 准备工作            —— 环境、依赖、配置（用 checklist 呈现前置条件）
3. 步骤（steps 组件）  —— 每步：标题 + 说明 + 预期结果（+ 代码块）
4. 验证 / 常见错误     —— 完成后如何自测；出错的坑 + 对策（callout: warning）
5. 扩展或下一步        —— 可选：进阶用法
6. 参考来源
```

要点：
- 步骤用 `steps` 组件，**每步都给「预期结果」（`.step-result`，与步骤同框）**——
  做完这步该看到什么，读者才知道自己没走偏（评测反馈特别点名要求）
- 命令用代码块，紧跟所属步骤；运行前交代前提（工作目录、权限）。终端命令用
  `lang-bash`，复制时会自动剔除 `$` 提示符；需要逐行引用时加 `<pre class="linenos">`
- 「常见错误」不是可选项：这是教程最有价值的部分之一。每个坑配 `callout: warning`
- 前置条件用 `checklist`，让读者先打勾确认
- **可选步骤 / 进阶内容用 `<details class="fold">` 折叠**（渐进披露），主线保持干净；
  主线步骤必须直接可见，别用折叠藏主线

## B. explainer 知识讲解

**适用**：解释概念、机制、原理；用户刚问过「XX 是什么/怎么运作」的回答转成页面。

推荐章节骨架：

```
hero（标题/对象）
1. 一句话结论           —— 开头直接给核心答案，别让读者翻到最后才懂
2. 为什么重要 / 背景     —— 场景、动机、解决的问题
3. 核心概念 / 原理       —— 分解概念，用卡片网格收术语；用示意图/类比讲机制
4. 工作原理（可选）     —— 机制类内容：按「输入→处理→输出」讲，配合图表
5. 关键要点 / 误区       —— 要点回顾；常见误解用 callout: warning
6. 示例或类比           —— 一个贴近生活的例子，帮助建立直觉
7. 参考来源
```

要点：
- 开头一句话结论最重要，**先给答案再讲道理**
- 机制类内容优先用图：有「是/否判断」的流程用 `.flow` 流程图、事件按时间展开用 `.timeline`
  时间线、循环往复用 `.donut` 做 cycle、复杂交互/状态迁移用 mermaid 预渲染 SVG
  （design-system §4.32 / §4.33 / 附录），别硬塞依赖库的图表
- 术语首次出现给粗体 + 简短定义；集中出现的术语收进卡片网格
- 讲解篇幅控制：正文段落短、小标题多，方便扫读

## C. decision 决策指南

**适用**：选型、对比、该选哪个方案/工具/配置。

推荐章节骨架：

```
hero（标题/决策问题）
1. 决策背景与目标        —— 这个选择在什么场景下做；决策标准是什么
2. 候选方案一览          —— 卡片网格或对比表，先给全貌
3. 逐项深比              —— 每个维度（性能/成本/易用性/生态…）拉平比较
4. 综合对比表            —— 维度 × 选项 的表格（组件 4.8）
5. 结论与推荐            —— 明确给出推荐路径 + 理由；给出决策树或 if-then 建议
6. 实施要点（可选）      —— 选定后的第一步怎么走
7. 参考来源
```

要点：
- **结尾必须有明确推荐**，可以带条件（「若你追求 X 选 A，若追求 Y 选 B」），
  但绝不能让读者读完还悬着
- **结论要能直达**：目录里「结论与推荐」置顶或加锚点，hero 用 `jumps` 组件放
  「直接看结论 →」「综合对比表」「决策小测」跳转按钮（样式统一）
- 对比表的维度要**真实对应读者的决策标准**（§1 里定的），别堆不痛不痒的字段
- 「适合谁」放每项候选里，而不是笼统一句话
- **决策小测必须可用**：用骨架的 `.quiz` 组件（5 题左右，单选对应方案 A/B），
  点"看结果"必须自动给出结论——不要让用户自己对照（评测反馈点名：选完要弹结论）。
  不要手写复杂交互

## D. reference 参考手册

**适用**：速查、术语表、配置清单、命令/API 一览。这类页面最像「文档」，
结构最直接：

```
hero
1. 快速总览（可选）      —— 一张表概括全部条目
2. 条目列表              —— 术语表/配置/命令，每个条目：名称 + 说明 + 示例
3. 常见组合或用法模式    —— 可选：条目之间的关联
4. 参考来源
```

要点：
- 条目统一成卡片网格（名称 + 说明）或表格（名称 + 说明 + 示例），**全页保持一致**
- 锚点链接：每个条目给 `id`，侧边目录按字母/分组列出，便于直达
- **速查表（命令/配置/术语）必须提供搜索框**：`<div class="sticky-toolbar"><input class="search-box" data-filter-target=".card"></div>`，
  搜索栏吸顶固定（不随滚动走），按类别分组 + 可搜索过滤（评测反馈：真正的速查表要有搜索、搜索栏固定最上方）

## E. code-guide 叠加态

不单独成页，而是叠加在上述类型之上。当内容含大量代码时：

- 代码块一律带语言标签 + 可复制
- 长代码拆段讲解：先给「这段做什么」再给代码，避免整屏代码糊脸
- 目录结构用等宽的 `tree` 块呈现
- 涉及配置时给「最小可用示例」而不是完整工程

## 类型混用速查

| 主体 | 可叠加 | 示例 |
|---|---|---|
| procedure | code-guide、reference（速查附录） | 安装教程 + 命令速查附录 |
| explainer | procedure（演示一段操作）、decision（顺带对比） | 讲 TCP 原理 + 一次抓包演示 |
| decision | code-guide（选型后给一段示例） | 选 ORM + 最小示例 |
| reference | explainer（条目外给原理概述） | 命令手册 + 前置原理 |

判断每处该用什么组件时，回到 design-system §4：**组件服务于内容**。

## 专业领域版式速查（跨类型）

同一份内容套不同"专业语境"时，读者预期的是该领域通行的视觉语言。选主题时先对号入座，
再按领域的排版侧重补组件。总原则仍是 **form follows function**——数据页别套装饰过重的主题。

| 领域 | 推荐主题 | 排版侧重 | 常用组件 / 结构 |
|---|---|---|---|
| 学术 / 论文 | `book`（或 `modern`+serif 正文的 `academic`） | 衬线正文、两端对齐、编号标题、克制的纸墨配色 | 摘要 callout、参考文献区、术语注记 `.term`、`<sup>[n]</sup>` 可点引用 |
| 法律 / 规范 | `book` | 密排、条款化编号、结构分明、少装饰 | 编号列表、`details.fold` 折叠细则、条款对照表、footer 版权行 |
| 财经 / 数据 | `swiss`（或 `minimal`） | 数字先行：tabular-nums、大数字锚点、发丝线表格、无多余网格（data-ink） | `.stat` 大数字、`.barchart` / `.donut`、表格 + 图注、数据截至标注 |
| 工程 / 技术规范 | `tech`（或 `swiss`） | 精密层次、代码高亮、可扫读的表 | `pre.linenos`、`.flow` 流程图、`.timeline`、调用约定表格 |
| 产品 / API | `tech` | 主色引导路径、步骤清晰、错误处理可见 | `.steps`、⚠️ `.callout`、chips 参数、`.takeaway` |

各排版侧重的具体规则（行长 / 行高 / 缩进 / data-ink / 孤行寡行）见 design-system §2.3；
主题的血统与视觉签名见 design-system §2.2。
